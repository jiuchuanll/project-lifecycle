# 知识对齐 Feedback 设计

状态：已批准

日期：2026-08-12

仓库：`jiuchuanll/project-lifecycle`

已选方案 ID：`solution-dual-truth-feedback-deferred-routing`

英文原文：[2026-08-12-knowledge-alignment-feedback-design.md](./2026-08-12-knowledge-alignment-feedback-design.md)

## 目标

让项目知识首次构建与后续知识维护能够在代码仍与业务决定不一致时，记录已确认的业务决定，同时保留实现证据、立即捕获一份持久 Feedback、默认继续当前知识流程，并将 PRD 或非 PRD 交付的创建推迟到用户明确选择交付路线之后。

## 问题

知识发现期间，代码可能支持某项能力，但用户确认它已经废弃、无效或不再属于认可的业务模型。此时同时存在三个不同判断：

- 被检查的代码基线中确实存在相关实现；
- 用户已确认该能力不再受业务支持；
- 交付流程尚未修改或验证实现。

只把代码当成真相，会错误地把废弃能力继续保留为已认可的业务知识。把期望业务模型当成已经实现，则会错误声称运行时已经完成对齐。立即创建 PRD 又会打断知识构建，并把 Feedback 捕获和交付授权混为一谈。

## 已确认原则

- 规范知识同时记录已确认的业务决定和已验证的实现状态。
- “废弃”等业务决定经明确确认后就是当前事实；实现移除只有在交付与验证证明后才是当前事实。
- 已确认的业务—实现差异必须立即创建持久 Feedback。
- 捕获 Feedback 不会创建 PRD、启动交付、分配工作树或修改代码。
- 首次建库与后续维护使用同一模型。首次建库通常在收口审阅前延迟交付路由；后续维护通常在当前维护批次收口，除非用户要求立即交付。
- Agent 推断的 PRD 或非 PRD 创建由用户决定。
- 活动聚合是稀疏派生投影，不是第二事实源，也不是追加式项目日志。

## 认知模型

知识资产必须使用精确判断，不能只写含糊的“功能已废弃”。例如：

> 已认可的业务模型不再支持旧审批入口。代码基线 `abc123` 中仍保留相关实现；运行时是否已经完全停止暴露该行为尚未验证。整改由 `feedback-legacy-approval` 跟踪。

这个表述包含三个可以独立成立的事实：业务决定已确认、实现已观察到、对齐尚未完成。它不能声称代码或运行时行为已经移除。

继续使用现有能力文档结构，不增加能力 Frontmatter 字段，也不增加新的全局知识状态：

- **当前事实**记录已确认的业务处置。
- **实现与资源地图**保留最小的当前实现入口。
- **已知限制与未知项**记录尚未解决的对齐差异并链接 Feedback。
- **来源**引用人工决定、检查过的基线和支持证据。

如果现有事实仍表示同一个语义主题，则保留 `fact_id` 并提升 `fact_revision`。临时实现差异通常进入已知限制，不额外分配事实 ID。只有实现状态本身具有独立、长期检索价值时，才创建单独的实现状态事实。

## 所有权与资产

`maintain-project-knowledge` 负责知识候选、中英文能力资产、基线以及已接受 Knowledge Diff 的回写。`run-prd-lifecycle` 负责 Feedback、PRD 与非 PRD 交付资产、验证证据、关闭以及候选 Knowledge Diff。

持久事实源是 `docs/project-lifecycle/delivery/` 下正常的中英文 Feedback 对。不可变来源区段保存原始问题、场景和期望；可变的“标记”区段保存受控的业务—实现对齐标记和当前覆盖信息。该标记只包含对齐分类、一个 `primary_domain_id` 和可选的明确暂缓处置，不保存 Owner 进度、证据正文或历史。已经表示同一个原始问题的 Feedback 应复用，不重复创建。

中英文活动投影生成到：

- `docs/project-lifecycle/delivery/alignment-review-en.md`
- `docs/project-lifecycle/delivery/alignment-review.md`

这两个文件是派生视图。Feedback、交付 Owner、关闭摘要和已接受知识仍然是权威来源。

`pending-changes.json` 继续只保存开放的知识拓扑、所有权、约束、关系和语义事实提案，不能成为代码整改或产品交付待办列表。

## 仅捕获 Feedback

活动知识任务保持 `KNOWLEDGE_UPDATE` 为主路线。当用户明确确认一个重要的业务—实现差异时，知识流程只向 `run-prd-lifecycle` 执行一次有界移交：

1. 保存或创建中英文 Feedback 事实源。
2. 将其标记为活动的对齐差异。
3. 把控制权返回知识构建。

这个有界移交不得物化 PRD、非 PRD 交付 Owner、Context Receipt、批次、工作树、代码变更或测试执行。契约是：

```text
Feedback captured != PRD materialized != delivery started
```

如果用户明确要求立即整改，仍然先捕获 Feedback，然后由 Agent 提出最小且合理的 PRD 或非 PRD 边界。Agent 推断的交付 Owner 在用户确认前不得物化。

## 活动对齐投影

每个活动行严格包含五个字段：

| 字段 | 含义 |
| --- | --- |
| `feedback_id` | 指向权威 Feedback 对的稳定链接。 |
| `title` | 在各语言中用一行本地化标题说明对齐差异。 |
| `primary_domain_id` | 用于分组的规范领域。 |
| `alignment_phase` | 四个活动投影阶段之一。 |
| `owner_ref` | 排序去重的 PRD/非 PRD Owner 引用；路由前为空列表。 |

活动投影阶段只有四种：

- `REVIEW_REQUIRED`：Feedback 已存在，仍需用户进行路由审阅。
- `DELIVERY_OPEN`：已确认交付 Owner，但交付尚未被接受。
- `KNOWLEDGE_WRITEBACK`：交付已接受，但 Knowledge Diff 尚未解决并应用。
- `DEFERRED`：用户明确延迟了路由或交付。

不存在 `COMPLETED` 行。完成项退出活动投影，持久历史保留在 Feedback 和关闭资产中。

投影值必须能够确定性生成。`feedback_id`、有界的本地化 H1 标题和 `primary_domain_id` 来自已验证的 Feedback 对及其受控标记。没有文档级标题的旧 Feedback 可以在首次获得标记时增加且仅增加一条有界的本地化 H1，其不可变来源段保持不变。两份投影的机器字段与行顺序一致，`title` 则来自对应语言资产。`owner_ref` 通过反向查找活动或已归档保留、且关系中覆盖该 Feedback 的已接受 PRD 或非 PRD Owner 获得；使用列表可以在不增加第六个字段的情况下保留现有 Feedback/Owner 多对多契约。`alignment_phase` 根据完整 Owner 集合、其已接受关闭结果、Feedback 处置和外部验证的 Knowledge Diff 应用或无变更结果计算，不是可独立编辑的进度字段。

投影绝不能保存代码路径、证据正文、用户原始叙述、风险、PRD 范围、验收标准、测试结果、Knowledge Diff 正文、状态历史、Agent 推理或自由文本备注。这些内容必须留在各自的权威资产中。

## 投影生命周期

在首次构建或维护期间，新捕获的对齐 Feedback 以 `REVIEW_REQUIRED` 出现。收口审阅时，Agent 可以提出去重、合并、拆分、依赖顺序以及以下由用户控制的处置建议：

- 链接已有 PRD；
- 创建新 PRD；
- 创建有界的非 PRD 交付 Owner；
- 暂缓；
- 接受无需整改并记录关闭原因。

确认路由后，派生行变成 `DELIVERY_OPEN` 并填写 `owner_ref`。创建交付 Owner 不代表该行已经完成。只要任一必要的关联 Owner 仍开放，该行就保持 `DELIVERY_OPEN`；只有所有必要关联 Owner 都已接受关闭后，才进入 `KNOWLEDGE_WRITEBACK`，并持续到所有对应候选 Knowledge Diff 都被 `maintain-project-knowledge` 解决。

只有同时满足以下条件，条目才能退出活动投影：

1. Feedback 覆盖已有明确处置；
2. 实现整改或明确的“不整改”决定已被接受；
3. 发生交付时，交付验证与剩余风险处理已经完成；
4. Knowledge Diff 应用、明确的无变更结果或已接受剩余差异结果具有精确的外部验证绑定；
5. 规范知识准确表示最终业务与实现对齐状态，包括有意识接受的剩余差异。

仅创建 PRD、合并代码或关闭 PRD 都不是退出条件。

## 首次构建与持续维护

首次构建采用批量延迟策略：捕获 Feedback 并继续知识校准，除非即时风险或用户明确要求导致必须停止。初版知识构建完成后，对所有 `REVIEW_REQUIRED` 项进行一次有界路由审阅。初版知识可以在存在开放对齐 Feedback 时进入 current，因为双轨表述已经准确记录了尚未解决的实现状态。

后续维护使用相同资产和阶段。通常在当前维护批次结束时展示未解决项。只重新打开受影响的事实、限制、关系和领域；不相关的 current 知识继续可用。用户明确说“现在整改”时，在捕获 Feedback 后立即路由。

安全、合规、数据破坏或阻断当前任务的差异必须立即展示，不能静默延迟，但下一步获授权的动作仍由用户选择。

## 去重与基线漂移

如果活动或保留的 Feedback 已经保存相同原始问题和语义目标，不得再创建另一个 Feedback。通过允许更新的标记或覆盖路径附加新的当前证据，并复用现有投影行。如果无法确定两者等价，则并列保留并请求用户判断，不能合并来源历史。

如果代码基线在路由或关闭前变化，应保留不可变的 Feedback 来源区段，刷新当前实现证据并重新计算投影阶段。如果其他变更已经解决实现差异，仍然需要完成验证和知识回写才能让该行退出。业务决定发生变化时使用勘误或后继关系，不能重写原始叙述。

## 写入顺序与失败处理

使用以下安全持久写入顺序：

1. 创建或保留中英文 Feedback 对；
2. 用精确双轨表述更新中英文知识候选；
3. 重新生成中英文活动投影；
4. 验证标识符、基线、链接、阶段和中英文一致性。

Feedback 捕获失败时，必须阻止对应双轨知识的提升，否则交付差异会失去跟踪。知识更新失败时保留 Feedback 以便重试，且不得报告 current 知识已经更新。投影生成失败不能删除或改写权威 Feedback 或知识，但本次操作仍未完成，必须报告派生视图失败。

损坏或未被接受的 Owner 引用不能让行进入 `DELIVERY_OPEN`。交付关闭但 Knowledge Diff 未解决时仍保持 `KNOWLEDGE_WRITEBACK`。去重判断不确定、“废弃”含义不清或存在实质不同的路由候选时，使用 `NEEDS_USER`，不能静默推断。

## 有界规模与保留

投影从活动权威记录重新生成，而不是追加。展示时的分组和路由建议是临时结果，不持久化为正文。默认检索只包含活动行；关闭历史通过 Feedback、关闭摘要以及确有必要时的收据门控归档检索获得。

因此，它的规模取决于未解决差异数量，而不是历史迭代总数。每行都是固定且有界的结构，已完成工作贡献零行。

## 非目标

本设计不会：

- 把用户意图当作代码或运行时已经变化的证明；
- 强制每条 Feedback 都进入 PRD；
- 创建新的主路线、全局 obligation 存储或通用任务跟踪器；
- 把交付待办写入 `pending-changes.json`；
- 在投影中复制 Feedback、PRD、测试或 Knowledge Diff 正文；
- 在知识构建期间自动修改代码；
- 把已完成投影行保留为活动历史日志。

## 验证与验收

实现至少必须覆盖以下确定性与行为场景：

1. 用户废弃代码中仍存在的重要能力：创建 Feedback，不创建 PRD 或工作树，生成双轨知识，行状态为 `REVIEW_REQUIRED`，首次构建继续。
2. 用户要求立即整改：先创建 Feedback，Agent 推断的 PRD 或非 PRD Owner 在确认前不得物化。
3. 再次发现同一个差异：复用现有 Feedback 和投影行。
4. 交付开放：行状态为 `DELIVERY_OPEN` 并链接已接受 Owner。
5. 交付已接受但知识未回写：行状态为 `KNOWLEDGE_WRITEBACK`，不能退出。
6. Feedback 覆盖、交付验收和知识吸收全部完成：行退出，但 Feedback 与关闭历史保留。
7. 用户暂缓条目：行保持 `DEFERRED`，不累积执行历史。
8. 中英文 Feedback、知识和投影对的 ID、基线、阶段、链接和标题结构一致。
9. 没有移除证据：current 知识绝不能声称实现或运行时已经移除。
10. 大规模夹具包含大量已关闭 Feedback 和少量活动项：只渲染活动项，每行严格包含五个字段，证据或自由文本历史不会进入投影。
11. Feedback、知识或投影写入分别失败：操作报告准确的未完成阶段并保留之前的权威状态。
12. 发现高风险差异：要求用户立即关注，不能采用默认批量延迟。

## 实现边界

未来实现应保持克制。它可以扩展两个 Skill 的参考文档、Feedback 标记验证、一个有界的对齐投影生成器及其 schema、成对的生成资产以及聚焦的契约与行为测试。它应复用现有 Feedback 来源不可变性、交付关系、中英文验证、路线词表、Knowledge Diff 移交和索引生成约定，而不是引入另一套交付生命周期。
