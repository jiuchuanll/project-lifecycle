# 深度领域校准设计

状态：已批准

日期：2026-08-11

已选方案：`solution:deep-domain-calibration-protocol`

英文原文：[2026-08-11-deep-domain-calibration-design.md](./2026-08-11-deep-domain-calibration-design.md)

## 目标

优化 `maintain-project-knowledge`，使其能够按候选领域识别复杂度，帮助用户思考困难的边界与关系，并产出完整、简洁、具备证据支撑的知识，同时不从用户手中夺走语义决策权。

Skill 可以推荐 `superpowers:brainstorming`、`grill-me` 或内置等价协议。仅仅出现复杂度信号时，不得自动启动交互式深度思考流程；是否以及如何深化该领域由用户选择。

## 已确认决策

- 按领域评估复杂度，不把整个项目划分为简单或复杂。
- 将复杂度条件视为升级建议信号，而不是自动调用外部 Skill 的授权。
- 用户明确要求使用 Brainstorming 或 Grill Me 时，不重复询问同一个授权问题。
- 当多种实质不同的领域模型需要比较时使用 Brainstorming。
- 当已有候选模型但仍需压力测试高影响假设或补充用户知识时使用 Grill Me。
- 只有方案选择后仍存在重要未知项时，Brainstorming 才衔接 Grill Me。
- 安装任何缺失的全局能力前必须询问。用户同意深化领域，不等于同意修改全局插件环境。
- 安装被拒绝、不受支持、失败、来源不可信或当前会话尚未生效时，使用内置等价协议。
- 用户拒绝深化时仍尊重其主观能动性；安全继续、记录未解决风险，不把验证不足的知识提升为 `current`。
- 采用两遍收敛：先逐个深化已选领域，再审查完整候选地图的跨领域一致性。
- 推理过程和访谈记录保持临时性；只持久化已接受边界、已验证事实、简洁且长期有用的决策依据，以及影响未来工作的未解决缺口。
- capability 资产成为 `current` 前必须通过语义质量门；结构验证本身不充分。
- `project-map.json` 继续作为拓扑和路由的权威来源；不新增复杂度分数、访谈日志、全局事实索引或持久化工作流状态文件。

## 范围

本设计调整 `maintain-project-knowledge` 在引导初始化、校准、拓扑重新审视和能力知识物化期间的交互契约。它新增一份聚焦的深度领域校准参考，仅在领域信号或用户明确要求使其相关时连接到现有生命周期。

本变更还会增强行为场景和物化指导。它不会构建确定性的领域分类器，不会新增长期推理存储，不会修改 project-map schema，不会复制外部 Skill，也不会让插件安装成为知识构建的前提。

## 协议边界

新增 `skills/maintain-project-knowledge/references/deep-domain-calibration.md`，由它唯一负责：

- 领域级复杂度信号；
- 用户升级授权；
- Brainstorming、Grill Me 和内置模式路由；
- 能力发现与安装授权；
- 七个用户介入点；
- 主动思考提示；
- 两遍收敛审查；以及
- 语义内容质量复核。

`bootstrap-and-calibration.md` 继续负责证据收集、候选卡片和边界确认。`materialization.md` 继续负责证据门槛、真值状态、中英文资产和提升为 `current`。新协议只在这些责任方之间协调更深的推理，不成为新的知识或拓扑所有者。

只有需要解释复杂度建议、用户要求更深推理或到达第二遍审查时，主 Skill 才加载深度校准参考。边界清晰的普通工作必须保持轻量。

## 领域级复杂度信号

Agent 对每个候选领域执行有界风险扫描。该扫描是分析准备，不是对最终拓扑的自主决定。

出现以下一个或多个条件时建议 Brainstorming：

- 存在两种或以上实质不同且合理的拆分；
- 用途、边界或已知扩展方向尚未解决；
- 父子、并列或单领域建模会产生不同的未来路由；
- 仓库或模块布局与用户或业务能力相冲突；
- 新发现的能力可能实质改变已接受地图；或
- 用户表示需要更广泛地探索项目理解或方案空间。

出现以下一个或多个条件时建议 Grill Me：

- 用户已经提供地图或偏好的拆分，需要压力测试；
- 权威项目证据无法确定高影响业务边界；
- 所有权、依赖、父子关系、共享约束或传播仍存在争议；
- 证据冲突或依赖组织中的隐性知识；
- 错误答案会实质影响未来知识路由、PRD、架构或交付；或
- Brainstorming 已选择方案，但仍留下一个高影响假设。

对于措辞、格式、翻译、索引修复、一个可在本地回答的事实，或处于已接受设计下且没有新设计问题的工作，不建议完整深挖流程。只缺少一个有界事实时，只问一个聚焦问题。

## 建议与授权门

存在信号时，Agent 首先展示：

1. 受影响领域；
2. 已观察证据和明确标记的推断；
3. 复杂度信号及下游风险；
4. 推荐模式及预期解决的问题；
5. 可选项：推荐的外部 Skill、适用时的另一深挖模式、内置模式、暂缓或继续轻量流程。

然后 Agent 等待用户选择，不得把推荐描述成已经完成的决策。

一次批准覆盖当前领域、当前校准分支下选择的模式，不为每个小问题重复询问。只有从 Brainstorming 切换到 Grill Me、安装全局能力、实质改变候选方案、暴露跨领域影响、确认边界或把事实提升为 `current` 时再次询问。

用户拒绝深化时，继续工作且不反复劝说。保持未解决风险可见，只在出现新证据或风险开始影响后续决策时重新打开。知晓风险永远不能代替事实验证。

## 深度推理模式

### Brainstorming

Brainstorming 用于探索方案空间，必须：

- 确立领域预期负责的用户或业务结果；
- 提供两种或三种实质不同的领域模型；
- 比较范围、所有权、依赖、可扩展性和维护成本；
- 给出一个推荐模型、理由和明确取舍；
- 分段取得用户确认后，才把模型视为已选择。

### Grill Me

Grill Me 用于压力测试候选方案，必须：

- 先调查代码和文档，再询问用户；
- 一次只问一个问题；
- 解释为什么此刻需要该问题；
- 提供推荐答案及其主要代价；
- 顺着决策依赖逐项解决高影响分支；
- 达到足以进入下一道门的共同理解时停止。

### 内置等价协议

内置模式在不声称运行了不可用外部 Skill 的前提下，保留相同的交互语义。它的方案探索形式提供备选、取舍、推荐和分阶段确认；它的压力测试形式先调查，再一次提出一个带推荐答案的问题，并解决互相依赖的决策。

内置模式是一等降级路径。它可以不如专门安装的能力专业，但不得跳过授权、证据、用户主观能动性、两遍收敛或质量门。

## 能力发现与全局安装

只有用户选择深挖模式后才解析能力。

若选择的外部能力不可用，只有在宿主提供原生安装机制且已知准确、可信的插件选择器或来源时，Agent 才能建议全局安装。建议必须说明能力、插件来源、全局范围和可能的重新加载要求。

安装需要单独明确批准。批准后使用宿主原生插件工作流，再次检查发现状态。不得编辑插件缓存或复制 Skill 文件作为替代。如果仍未发现、来源未知、宿主不支持、安装失败或用户拒绝，则继续内置协议并简要说明降级。

当前知识任务绝不能只因可选外部思考能力不存在而被阻塞。

## 七个用户介入点

1. **初始覆盖校准：** 轻量候选地图形成后，用户修正项目意图、遗漏的业务能力和主要边界。
2. **复杂度升级建议：** 出现领域信号后，用户选择是否以及如何深化。
3. **方案选择：** Brainstorming 给出备选后，用户选择、组合、修改、拒绝或暂缓。
4. **隐性知识问题：** 证据无法回答高影响问题时，用户一次补充一项业务、团队或未来方向知识。
5. **领域边界确认：** 用户确认、改名、拆分、合并、拒绝或暂缓候选领域。
6. **整体地图一致性复核：** 第二遍结束后，用户处理重要缺口、重叠、层级错误、共享所有权和扩展风险。
7. **当前真值提升：** 语义事实成为 `current` 前，用户审查准确事实、证据、限制和受影响领域。

全局安装是独立授权点，不能与以上任何批准合并。

## 主动思考提示

在一个介入点，只选择与当前决策最相关的问题，不倾倒通用问卷。问题应包含该问题为什么重要、证据已经证明什么、推荐答案，以及接受它的主要代价或风险。

有用的问题包括：

- 该领域负责什么用户或业务结果？
- 哪些内容明确不属于其边界？
- 它能否在不改变另一个领域含义的情况下独立演进？
- 该关系是真正的包含，还是横向协作？
- 谁负责共享数据、接口或约束？
- 如果该领域消失，哪项职责会无人负责？
- 下一个已知扩展会自然落到哪里？
- 这项主张是已实现的当前真值、已接受设计，还是未来计划？
- 未来谁会检索这项事实，用于什么决策？
- 删除这段文字是否会损失可复用知识？如果不会，就应省略。

Agent 可以准备并推荐，但不得静默把推荐转化为用户接受。

## 两遍收敛

第一遍创建轻量的项目级候选地图，逐领域评估，只深化用户授权的领域，并确认各自边界。

第二遍审查完整候选地图中的：

- 遗漏的核心能力；
- 重叠或无人负责的职责；
- 并非真正包含关系的父子结构；
- 被建模为层级的横向依赖；
- 不清晰的共享能力、数据、约束或仓库所有权；
- 无法自然落入当前结构的已知扩展；以及
- 一个领域变化时未声明的下游影响。

审查发现问题时只重新打开受影响领域，无关的已确认边界继续可用。写入或改变骨架前，用户复核重要发现。

## 临时推理与持久知识

复杂度评估、访谈记录、被放弃的备选方案和完整推理链保留在对话中，不成为规范项目知识。

持久写入仍然限定为：

- `project-map.json` 中已接受的领域骨架和关系；
- 中英文 capability 资产中已验证的当前事实；
- 只有在会影响未来路由或解释时才保留的简洁决策依据；以及
- 影响未来工作的明确缺口、限制和未知项。

未解决的语义候选使用现有审核和 pending-change 机制。不得创建深度校准日志，也不得在 capability 文档中复制 PRD、测试、实现或历史叙述。

## 语义内容质量门

capability 资产成为 `current` 前，必须通过全部六道门：

1. **边界清晰：** 用途、包含项、排除项以及与父级和同级的差异易于理解。
2. **持久事实覆盖：** 最可能支持未来检索和决策的稳定事实已经存在，且没有占位文字。
3. **证据质量：** 每项当前事实都有支持证据、验证基线和与风险相称的明确限制。
4. **关系清晰：** 规范所有者、父子关系、主要依赖、共享约束和仓库所有权明确。
5. **扩展准备：** 稳定身份、可能的变化接缝、已知扩展、未知项和未解决风险清楚。
6. **内容精炼：** 资产通过链接而非复制 map、Feedback、PRD、测试报告、交付或其他领域正文。

不得把这些门汇总为数值分数。任何关键门失败，资产保持不存在或非当前状态，并报告最小可执行缺口。结构验证证明契约完整性，但不能覆盖失败的语义门。

## 失败与停止处理

- 用户暂缓深化时，只在已验证范围内继续，并保留未解决风险。
- 证据无法确定高影响事实时，停止提升并提出一个聚焦问题或保留缺口。
- 用户拒绝全局安装时，切换到内置模式，不把拒绝安装视为拒绝深化。
- 安装成功但当前会话没有发现能力时，说明重新加载边界，并在本轮使用内置模式。
- 用户同时拒绝外部和内置深化时，不重复提示；只保留满足现有门槛的边界或事实。
- 第二遍发现语义冲突时，只重新打开受影响领域，并在持久拓扑变更前要求用户复核。
- 质量门失败时，不制造内容填充章节，也不把资产提升为 `current`。

## 实现边界

实现应以声明式契约和行为覆盖为主：

- 新增聚焦的深度领域校准参考；
- 从 `maintain-project-knowledge/SKILL.md` 路由到它；
- 将 bootstrap/calibration 与 materialization 指导连接到其授权、第二遍和质量门；
- 仅在确有必要时调整 capability 模板，使边界和持久事实更容易复核；
- 增加 Skill 契约和 Gold 行为覆盖；
- 保持中英文模板或设计文档同步。

不得新增运行时评分引擎、新 CLI 命令、复杂度 schema 字段或持久化对话账本。现有验证器可以执行稳定结构信号，但语义意图仍由 Agent 与用户共同掌握。

## 验收标准

- 按领域评估并解释复杂度。
- 复杂度信号产生建议和授权问题，而不是自动调用外部 Skill。
- 用户明确要求时，直接进入所选模式而不重复确认。
- Brainstorming 与 Grill Me 具有不同且可测试的路由条件。
- 内置降级保留已批准的交互和质量门。
- 未经独立明确批准和可信准确来源，不进行全局安装。
- 拒绝深化不阻塞安全进展，也不允许未验证事实成为当前真值。
- 七个介入点保留用户对语义决策的所有权。
- 主动思考提示聚焦、基于证据并提供推荐。
- 第二遍发现跨领域缺口时，不重新打开无关领域。
- 推理记录不会成为规范项目知识。
- 提升为 `current` 前必须通过全部六项语义质量门。
- 不新增持久工作流状态、复杂度分数或重复知识索引。
- 相关 Skill 契约、行为、中英文和回归测试通过。
